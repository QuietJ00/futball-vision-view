# 고정 구장 리플레이 검토

원본 카메라와 고정된 2D 구장을 함께 재생한다. 하늘색 점은 프레임별 YOLO 사람 검출, 노란 점은 클릭으로 지정한 한 선수의 추적 결과다. JSON은 프레임별 투영 행렬, 좌표, 속도 추정치와 검증 결과를 담는다. 이 경로는 독립 CLI다.

검증 기준을 벗어난 구간에는 원본 영상 위의 구장 선도 숨긴다. 검사 중 실패한 투영을 직접 보려면 `--show-unverified-overlay`를 켜면 주황색으로 표시한다.

## 녹지운동장 데모 재현

프로젝트 루트에서 의존성이 설치된 Python으로 실행한다. 캐시에는 `jobs/ye-0920-goal/`의 프레임, 카메라 움직임, 사람 검출이 필요하다.

```bash
python -m autohl.pitch_replay \
  --job ye-0920-goal --marks experiments/pitch_replay/ye_goal_marks.json \
  --lens-offset-m 0 --output outputs/ye_fixed_pitch_replay.mp4

python -m autohl.pitch_replay \
  --job ye-0920-goal --marks experiments/pitch_replay/ye_goal_marks.json \
  --lens-offset-m 0.12 --output outputs/ye_fixed_pitch_replay_offset.mp4

python -m unittest discover -s tests
```

## 다른 영상과 구장

```bash
python -m autohl.pitch_replay \
  --source /path/to/clip.mp4 --marks /path/to/marks.json \
  --length 105 --width 68 --lens-offset-m 0.12 \
  --output outputs/my_replay.mp4
```

- 길이와 폭을 미터로 입력하거나 `--venue noksi`처럼 등록된 구장을 고른다. 데모의 100×60m는 녹지운동장 프리셋이다. 다른 페인트 규격은 `--box-depth`, `--box-half`, `--ga-depth`, `--ga-half`, `--spot`, `--half-x`로 지정한다. `half`가 붙은 박스 폭은 전체 폭의 절반이다. 나머지 치수는 공용 템플릿 기본값을 사용한다.
- 로컬 영상은 한 번에 90초까지 처리한다. `--start`, `--end`로 자를 수 있다. 좌표는 디코딩된 1920×1080, 30fps 기준이며 프레임 번호는 자른 클립의 0부터 센다. 카메라나 줌이 바뀌는 촬영은 분리해 처리한다.
- 예제 JSON의 `fit`에는 프레임별로 실제 흰 선 위의 점을 여러 개 기록한다. 최소 두 프레임이 필요하고, 초기화에 쓰는 프레임 하나에는 서로 다른 직선 네 개 이상이 필요하다. `holdout`에는 보정에 사용하지 않은 프레임의 흰 선을 따로 표시한다. 최소 두 선이 있는 프레임만 품질 검사에 쓴다. `player_clicks`는 선택 사항이다.
- `fit_far_edges`와 `holdout_far_edges`는 선택 사항이다. 흰색 먼 터치라인이 희미하면, 그 터치라인이 실제로 존재할 수 있는 범위의 바깥쪽 경계인 잔디와 트랙의 접점을 표시한다. 피팅에서는 선이 그 경계보다 위로 나갈 때만 벌점을 준다. 독립 프레임에서 위쪽 이탈의 p90이 5px를 넘으면 근처 프레임의 좌표 표시를 보류한다.
- 선 번호는 `pitch.model_segments` 순서다. 0 왼쪽 골라인, 1 가까운 터치라인, 2 먼 터치라인, 3 오른쪽 골라인, 4 하프웨이, 5~7 왼쪽 박스, 8~10 왼쪽 골에어리어, 11~13 오른쪽 박스, 14~16 오른쪽 골에어리어, 17 센터서클, 18~19 페널티 아크다. 각 박스의 선 순서는 가까운 쪽, 앞쪽, 먼 쪽이다.

## 모델과 실제 결과

구장 치수와 렌즈 오프셋은 입력값으로 유지한다. 삼각대 피벗 `A`와 초점거리 `f`를 여러 프레임의 흰 선으로 공동 추정한다. `Rᵢ`는 월드에서 카메라로 가는 회전이다. 광축 방향 오프셋 벡터가 `r = (0, 0, d)`이면 프레임의 렌즈 중심은 `Cᵢ = A + Rᵢᵀr`이다. 팬에 따라 `Cᵢ`가 움직인다. 현재 구현은 피벗 하나와 광축 방향 거리 하나를 사용한다. 축의 기구적 분리, 가로·세로 렌즈 오프셋, 줌 변화와 렌즈 왜곡은 이 실험 범위 밖이다.

여러 키프레임을 공동 피팅한 뒤 영상에서 얻은 움직임을 이용해 중간 프레임의 회전을 계산한다. 카메라 추적이 끊긴 구간에는 좌표를 내보내지 않는다. 기본 표시 조건은 가장 가까운 독립 체크가 2.5초 이내이고, 그 프레임의 모든 표기 선에서 재투영 오차 90백분위가 10px 이하다. 중간 프레임에는 이 결과를 전파한다.

잔디 경계 검사를 추가하기 전의 09:20~09:30 데모에서 오프셋 0m와 가정값 0.12m가 모두 **265/300 프레임**을 표시했다. 각 설정에서 선택 선수 좌표는 186프레임, 1초 속도 추정치는 62프레임이다. 검증 프레임 150, 260, 320은 통과했고 389의 박스 옆선은 p90 약 13.2px로 실패했다. 두 설정의 차이는 작았고 실제 렌즈 거리는 미측정이다. 실측 선수 위치나 속도 정답도 없다.

프레임 245~275에서 동일한 선수 발 관측 24개를 썼을 때 새 오프셋 모델은 22.91km/h, 이전 수동 보정의 `270_box_and_boundaries`는 25.30km/h를 냈다. 이 비교는 카메라 보정 차이만 보여준다. 독립 페인트 검사는 속도 정확도의 대용으로 사용하지 않는다.

잔디 경계 검사를 추가하기 전, 동일한 로컬 원본을 캐시 없이 읽어 카메라 추적과 YOLO를 다시 실행한 결과는 `outputs/ye_fixed_pitch_fresh.mp4`와 JSON에 있다. 이 실행은 **180/300 프레임**을 표시했다. 프레임 260의 박스 앞선 p90이 캐시 실행의 8.6px에서 10.9px로 달라지며 10px 기준을 넘었다. 캐시와 재실행의 차이는 현재 검토 항목이다.

후속 잔디 경계 보정은 `outputs/ye_fixed_pitch_touchline.mp4`와 JSON에 저장했다. 새로 계산한 카메라 추적값과 기존 YOLO 검출을 조합했으며, 새 피팅 프레임 295와 수동 경계 표시를 추가했다. 박스 옆선의 기존 확인점은 실제 페인트 중심을 다시 읽었다. 캡처와 같은 프레임 305에서 트랙 쪽 이탈 p90이 **20.2px → 4.3px**로 줄었다. 잔디 경계는 가능한 범위의 상한만 검증하므로, 흐린 흰 터치라인 자체의 정확도는 별도로 확인해야 한다.

중간 재측정본은 `outputs/ye_fixed_pitch_gap_remeasured.mp4`와 JSON이다. 같은 모델에 피팅 프레임 277을 추가하고, 230·254·260·280의 페인트와 잔디 경계를 독립 검사했다. 150과 260의 기존 확인점은 원본 페인트 중심을 다시 읽었다. 기존 10px/5px 기준으로 재측정본의 구장 좌표계가 **300/300프레임**에서 사용 가능해졌다. 원래 빠졌던 206~290프레임 중 선택 선수 발은 **49프레임**, 유효한 1초 속도는 **7개**였다. 가장 빠른 1초 추정치는 234~264프레임의 **27.62km/h**이며 발 관측 25개를 사용했다. 278~288프레임에서는 선수가 겹쳐 발 좌표를 보류했다.

센터서클 후속 보정은 `outputs/ye_fixed_pitch_center_aligned.mp4`와 JSON에 있다. 중앙의 실제 흰 선을 105·120·180에 표시해 피팅하고 100·143·150·170을 별도 검사했다. 이전 100의 피팅 표기를 독립 검사로 교체했고, 150은 흰 선 중심을 다시 읽었다. 잔디 경계 이탈 벌점도 1.35배로 조정했다. 같은 143프레임의 확인점 기준으로 센터서클 p90은 **16.2 → 5.4px**, 하프웨이는 **8.1 → 2.0px**였고, 300프레임의 구장 좌표계를 계속 제공한다. 같은 234~264프레임의 속도 추정치는 **26.93km/h**로 바뀌었다.

초반 먼 터치라인 보정은 `outputs/ye_fixed_pitch_early_edge.mp4`와 JSON에 있다. 초반의 105·120·180 잔디 경계를 피팅에 추가하고 90·100·135·143·150·165·170에서 별도 검사했다. 첫 프레임에서 트랙 방향 이탈 p90은 **16.4 → 3.8px**였고, 전체 300프레임의 좌표계 제공을 유지했다. 초반 화면 오른쪽 페널티박스는 실제 흰 선을 식별할 수 있는 확인점이 없어 별도 검증이 필요하다.

팬 중 센터서클 보정은 `outputs/ye_fixed_pitch_pan_stable.mp4`와 JSON에 있다. 195·215·240에 원본 페인트 기준을 더하고, 205의 센터서클·하프웨이 기준을 다시 읽었다. 인접 기준 프레임의 가중치를 시간에 따라 전환하고, 센터서클 주변 지면에서 양방향 추적과 별도 특징점 검사를 통과한 카메라 움직임을 회전 보정에 함께 사용했다. 독립 프레임 190과 235에서 센터서클 오차 p90은 각각 **12.8 → 4.2px**, **12.1 → 7.5px**였다. 프레임 220의 잔디 경계 p90은 5.6px라서 인근 10프레임의 좌표를 보류했다. 234~264프레임의 1초 속도 추정치는 **25.14km/h**다.

## Claude에 전달할 검토 요청

> `autohl/fixed_pitch.py`, `autohl/pitch_replay.py`, `tests/test_fixed_pitch.py`와 데모의 JSON을 검토해 줘. 고정 피벗과 광축 오프셋의 부호 및 단위, 카메라 움직임으로 회전을 전파하는 부분, 카메라 추적 실패와 독립 체크 실패 때 좌표 및 속도가 차단되는지를 확인해 줘. 특히 프레임 260에서 캐시와 새 실행이 갈리는 이유, 프레임 389의 박스 오차, 0cm/12cm 차이를 재현해 줘. 입력에 없던 먼 터치라인과 실제 구장 고정점으로 평가를 추가할 수 있는지도 봐 줘. 데모의 보정 선은 수동으로 표시했다.
